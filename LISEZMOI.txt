================ DONNÉES EXCEL PUBLIÉES AVEC LE SITE ================
Le site charge automatiquement, à l'ouverture, les deux classeurs du dossier data/ :
    data/R2_Data.xlsx   -> Chart Pack (et catalogue de séries du Chart Creator)
    data/Risk_Map.xlsx  -> AM Dashboard (feuille « Copy Risk Map » + ses graphiques)
    data/manifest.json  -> décrit ces fichiers (nom, date, empreinte) ; généré par le script.
Plus rien à glisser-déposer ni à lier : les glisser-déposer restent possibles (ils s'ajoutent / remplacent le temps de la session).

Pour mettre les données à jour :
  1. Mettre les classeurs à jour dans un dossier  data_source/  à la racine de CI (« R2 Data.xlsx », « Copy fixed Cycle and ESI.xlsx »…).
     Ce dossier n'est PAS publié : ajoutez la ligne  data_source/  dans votre fichier .gitignore (les originaux pèsent ~100 Mo).
  2. Lancer :   node prepare_data.mjs
     (aucune installation nécessaire ; reconnaît chaque classeur à ses feuilles ; les originaux ne sont pas modifiés)
        - Risk Map : le classeur d'origine (86 Mo, 485 Mo décompressé) dépasse la limite de Cloudflare (25 Mo par fichier) : le script n'en garde
          que la feuille « Copy Risk Map » et ses graphiques -> ~3 Mo, chargé en 2-3 secondes au lieu de 1 à 2 minutes.
        - R2 Data : toutes les feuilles sont gardées (~13 Mo).
  3. git add data && git commit -m "Mise à jour des données" && git push
  4. Déploiement : soit  npx wrangler deploy  à la main, soit automatiquement à chaque push (recommandé) : dans le tableau de bord Cloudflare,
     Workers & Pages > ci > Settings > Builds > « Connect » le dépôt GitHub (LaYeuk/CI), commande de déploiement :  npx wrangler deploy
     Dès lors, chaque « git push » met le site à jour tout seul.
Remarque : les fichiers de data/ sont aussi publics que le site lui-même (adresse /data/R2_Data.xlsx). Si ces données doivent rester confidentielles,
il faut protéger le site avec Cloudflare Access (je peux détailler).

================ MARKET DATA (nouvel onglet) ================
Cotes et historiques de marché via l'API tierce « TradingView Data API » (tradingviewapi.com ; clés sur console.tvapis.com).
Service NON officiel (sans lien avec TradingView) : données possiblement différées.
  1. Créer la clé sur https://console.tvapis.com/api-keys (ne la collez ni dans le dépôt, ni dans une discussion).
  2. Dans le dossier CI :   npx wrangler secret put TV_API_KEY      puis coller la clé. (Effet immédiat.)
  3. Recharger le site, onglet « Market Data ». Sans clé, l'onglet affiche ces instructions.
La clé reste sur le Worker : elle n'est jamais envoyée au navigateur. Le Worker n'accepte que les appels venant du site lui-même.
Économie de quota (forfait Basic = 150 appels/mois, Pro = 40 000) : réponses mises en cache dans D1 et partagées entre collègues
(cotes 60 s, bougies journalières 15 min, hebdo/mensuelles 1 h, recherche 24 h) ; compteur d'appels affiché dans l'onglet ;
plafond de sécurité 30 000 appels/mois (variable TV_MONTHLY_CAP pour le changer : Cloudflare > Workers > ci > Settings > Variables).
Avec le forfait gratuit (150 appels), la watchlist de 10 symboles ne coûte qu'1 appel par actualisation (toutes les 60 s au plus).
Onglet « SPI par secteur » : ~200 titres du Swiss Performance Index en 15 secteurs ; les cotes d'un secteur ne sont chargées qu'à son ouverture
(≈ 1 appel par 10 titres ; « Charger toutes les cotes » ≈ 21 appels). La composition est dans Outils_GIP.html (tableau MKT_SPI) et se met à jour à la main
lors de la révision annuelle de l'indice ; un ticker sans cote est signalé « sans cote ».
Watchlist : partagée par toute l'équipe (D1) ; clic sur une tuile = fiche (bougies jour/semaine/mois/1 h, ligne ou chandeliers) ;
« Ajouter au Chart Creator » envoie la clôture dans le groupe « Market Data » du Chart Creator.
